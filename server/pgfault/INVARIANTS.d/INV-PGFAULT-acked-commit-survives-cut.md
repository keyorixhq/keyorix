- **INV-PGFAULT-acked-commit-survives-cut** A TCP connection fault (cut or stall) between keyorix's storage layer and a real PostgreSQL server, injected at any point of the v3 wire protocol — including the ambiguous-commit window (COMMIT sent, acknowledgement not yet received) — must leave the audit store in an all-or-nothing state on reconnect: every `LogAuditEvent` that returned nil (the client saw the commit acknowledged) is still present, the hash chain still verifies (no torn row, no broken link), and a commit that errored is either absent or a legitimate present-but-unacknowledged row — never an acknowledged-but-absent one (a false success). A fault can only ever error the ONE in-flight commit; it can never unmake a commit the server already acknowledged. Why: FS-PG — the PostgreSQL counterpart to scripts/powercut's SQLite durability oracle; the durability story for an enterprise (PG-backed) deployment. Guard: `server/pgfault` `TestPGFault_ConnectionCut`, `TestPGFault_StallThenCut` (oracles hold under cuts/stalls at swept protocol points) and `FuzzPGFaultCommit` (same oracles over fuzzed cut points/burst sizes); red-proofs `TestPGFault_RedProof_FaultIsLoadBearing` (a cut actually leaves a commit un-acknowledged), `TestPGFault_RedProof_OracleDetectsLostAck` and `TestPGFault_RedProof_OracleDetectsBrokenChain` (each oracle goes red on its planted violation). PG-gated: skips without `KEYORIX_TEST_PG_DSN`.
