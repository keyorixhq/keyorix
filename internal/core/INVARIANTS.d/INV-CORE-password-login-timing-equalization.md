- **INV-CORE-password-login-timing-equalization** Every early-return path in
  `VerifyPasswordCredentials` (`auth.go`) that branches BEFORE the real
  `kdfmeter.CompareHashAndPassword` call on the stored hash must first execute
  an equivalent-cost dummy comparison —
  `kdfmeter.CompareHashAndPassword(*dummyBcryptHash.Load(), []byte(password))`
  — so that an unauthenticated caller cannot use response latency to
  distinguish "account does not exist" from "wrong password" (account
  enumeration via timing). `VerifyPasswordCredentials` has two such guarded
  paths: (1) the user-not-found / storage-error path (after
  `GetUserByUsername`), and (2) the login-locked path (`loginLocked`). The
  dummy hash is held in a package-level `atomic.Pointer[[]byte]`
  (`bcrypt_cost.go`); it is generated at the live `bcryptCost` (12 in
  production) and regenerated by `SetBcryptCostForTesting`, so its cost
  matches a real comparison in both production and test runs. The same rule
  applies to `verifyCurrentPassword` (`account.go`), which runs a dummy
  comparison on the login-locked path before comparing the actual stored hash.
  This is a cheap structural pre-check; the primary, behavioural guard of the
  same balance is `INV-CORE-login-kdf-cost-is-existence-balanced`
  (`FuzzKDFEnumerationOracle`: one compare, zero generations, across all
  existence classes). What this guard does NOT cover: response-time variation
  from network jitter, storage latency, or a cost mismatch between the dummy
  and a stored hash generated at an older cost; the guard is structural, not
  statistical.
  Guard: `internal/core/guards`
  `TestTimingEqualization_EveryPreCompareEarlyReturnSpendsDummy` (walks the
  top-level statements before the real comparison: every if-block that returns
  must reference `dummyBcryptHash` before its first return; 2 such blocks in
  `VerifyPasswordCredentials`, 1 in `verifyCurrentPassword`), plus the count
  checks `TestTimingEqualization_VerifyPasswordCredentials_DummyBcryptOnPreRealBcryptPaths`
  (exactly 2 `dummyBcryptHash` references) and
  `TestTimingEqualization_VerifyCurrentPassword_DummyBcryptOnLockedPath`
  (exactly 1). Confirmed red when a dummy call was removed, and (the walk)
  when the locked-path dummy was moved into the user-not-found block.
