- **INV-CORE-password-login-timing-equalization** Every early-return path in
  `VerifyPasswordCredentials` (`auth.go`) that branches BEFORE a real
  `bcrypt.CompareHashAndPassword` call must first execute an equivalent-cost
  dummy comparison — `bcrypt.CompareHashAndPassword(*dummyBcryptHash.Load(), []byte(password))`
  — so that an unauthenticated caller cannot use response latency to
  distinguish "account does not exist" from "wrong password" (account
  enumeration via timing). `VerifyPasswordCredentials` has two such guarded
  paths: (1) the user-not-found / storage-error path (after
  `GetUserByUsername`), and (2) the login-locked path (`loginLocked`). The
  dummy hash is a `bcrypt.MinCost` hash held in a package-level
  `atomic.Pointer[[]byte]` (`bcrypt_cost.go`), regenerated by
  `SetBcryptCostForTesting` in tests so its cost stays proportional to the
  cost of a real comparison in both production and test runs. The same guard
  applies to `verifyCurrentPassword` (`account.go`), which also runs a dummy
  comparison on the login-locked path before comparing the actual stored hash.
  What this guard does NOT cover: response-time variation from network jitter,
  storage latency, or bcrypt cost changes (the dummy is always MinCost in
  tests); the guard is structural, not statistical.
  Guard: `internal/core/guards`
  `TestTimingEqualization_VerifyPasswordCredentials_DummyBcryptOnPreRealBcryptPaths`
  (counts exactly 2 `dummyBcryptHash` references in `VerifyPasswordCredentials`)
  and `TestTimingEqualization_VerifyCurrentPassword_DummyBcryptOnLockedPath`
  (counts exactly 1 in `verifyCurrentPassword`). Both confirmed red when the
  respective dummy call was removed and green when restored.
