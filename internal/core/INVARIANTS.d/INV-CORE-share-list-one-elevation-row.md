- **INV-CORE-share-list-one-elevation-row** A share-list call (`ListUserShareViews`, `ListOwnedShareViews`: `GET /api/v1/shares`, `/shares/owned`) writes at most ONE `share_access_elevated` row: action `shares.list`, the count of secrets whose name the caller could read only through a share, and up to `shareListElevationDetailCap` (secret, share) pairs with `truncated` when cut. It never writes one row per secret on the page, and a caller whose role covers every read writes none. A real elevated use of one secret (its value read, an allowlisted write) is still audited per action by `AuthorizeSecretAction` / `CommitShareElevations`.
  Why: #3456 — the list ran its batch decision with no request recorder, so `noteShareElevation` audited each share-granted read at once: one row per received share every time the page opened.
  Guard: `internal/core/share_list_elevation_audit_test.go` (`TestListUserShareViews_WritesOneElevationRowPerListCall`, `TestListUserShareViews_RoleReaderWritesNoElevationRow`, `TestShareElevatedSecretRead_StillWritesItsOwnRow`), `share_list_elevation_audit_bound_test.go` (`TestListUserShareViews_SummaryRowIsBounded`).
  **Not covered**: the row is written when core returns the list; a transport refusal after that (the aggregate MFA check in the handler) does not remove it, the same timing the per-row rows had.
