- **INV-TIMETRAVEL-oracle-no-new-leniency** The mutation oracle must fail when the repo-pinned ("new") `pkcs7.Parse` ACCEPTS an input the older oracle version REJECTED, and when the new version PANICS. The reverse directions (new stricter; new bounding work the old version did not, including the old version crashing on deep nesting; both-reject wording differences) are allow-listed and only logged. Why: new-more-lenient is the shape a signature/parse-verification bypass takes — an older, battle-tested parser refused a structure the current one now admits; that is the one cross-version change that can be a security regression rather than a hardening. A differential that failed on *any* divergence would drown that signal in the dozens of intentional hardening changes between versions (TT1 report §3). Guard: `FuzzPKCS7TimeTravelOracle` (`internal/libconformance/timetravel_pkcs7_fuzz_test.go`); red/green proof in the TT1 report §6 (plant a forced-accept in the new path → oracle fires; unmodified → green).
