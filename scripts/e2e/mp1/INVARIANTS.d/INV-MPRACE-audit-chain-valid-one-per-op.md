- **INV-MPRACE-audit-chain-valid-one-per-op** With mutating operations driven concurrently through several replicas, the audit hash chain read straight from the shared database verifies VALID — no gap (a missing serialized append) and no fork (two heads from two replicas racing the ADR-029 serialize-append advisory lock) — and every acknowledged `secret.created` lands EXACTLY ONE audit row (never zero = dropped append, never two = double-write). Why: the audit chain is the tamper-evidence backbone and its integrity under multi-writer load rests entirely on the advisory lock serializing appends; core writes the `secret.created` row as the last statement of the same `WithTransaction` that commits the secret, so an acknowledged create implies exactly one committed row (backlog I1, oracle #5). Guard: `TestAuditChainVerifies` + `TestAuditCountExactlyOne` (`scripts/e2e/mp1/oracles_test.go`, `audit_count_test.go`), both firing their creates concurrently across the replicas so the appends contend for the lock (3 rounds of 12 for the count); counts read with pgx; red/green on `auditCountViolation` in `TestRedProof_AuditCount` and on the exact-VALID verdict check in `TestRedProof_AuditVerdict`. Not run in CI: no workflow runs `-tags e2e ./scripts/e2e/mp1` against Postgres, so this guard holds only for manual runs.
