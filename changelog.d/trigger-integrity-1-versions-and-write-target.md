### Security
- **The trigger integrity check now also covers `system_metadata`, the table every role-permission generation bump writes (PostgreSQL, #3713).** The server's own database role could add a `BEFORE UPDATE` trigger that keeps the old generation, a rule, or forced row-level security that hides the generation row. Every bump then became a no-op, the check's own included, while the triggers and function it compared still read as correct, and a permission removed with direct SQL kept authorizing from warm caches. The 30-second check now also requires that `system_metadata` has no trigger except the audit retention-anchor one exactly as installed, no rule, and row-level security off. On a difference it logs a `SECURITY:` line, counts `reason="tamper"`, removes them and invalidates every replica's permission cache.

### Fixed
- **A rolling upgrade to a release that changes a trigger function no longer makes old and new replicas revert each other every 30 seconds (PostgreSQL, #3717).** Each checked trigger function now carries a version marker comment with a digest of its definition. A replica leaves a newer release's self-consistent definition (at most one version ahead) in place, on its checks and its boots. It logs a non-`SECURITY` warning, invalidates the cache once and increments the tamper counter under the new `reason="newer_definition"` label. Before, each side logged `SECURITY:` and re-installed its own definition every tick, with fleet-wide cache flushes, and older replicas could undo a security fix. `keyorix_role_permission_generation_tamper_total` and `keyorix_secret_node_cache_epoch_tamper_total` now carry a `reason` label (`tamper` or `newer_definition`), so alert on `reason="tamper"`, and on `newer_definition` outside a deploy. A missing, malformed or inconsistent marker is still tampering. Design and residual risk: `docs/design/trigger-rowdigest.md`.
