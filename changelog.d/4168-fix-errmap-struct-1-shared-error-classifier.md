### Changed
- **One classifier turns a core refusal into the HTTP or gRPC status (behaviour change on the routes below).** Handlers and gRPC services used to map core errors with per-route logic (substring matches on translated text, allow-lists ending in `default: 500`), so the same refusal was a 500 on one route and a 403 or 404 on its sibling (#4132, #3979, #4020). A shared classifier (`server/errclass`) now maps the core and storage sentinels to a closed set of classes, rendered by one REST adapter and one gRPC adapter, so the two transports agree by construction. Nothing changes in who is allowed; only the status and text of a refusal. Status changes for an existing request: `GET /api/v1/projects/{id}/machine-identities/{machineId}/tokens` for a machine in another project 500 → 404; `POST /api/v1/secrets/{id}/resume` when the secret's environment was deleted 500 → 404; `GET /api/v1/projects/{id}/stats` for a missing project 500 → 404; `POST /api/v1/secret-templates` with an over-long name or an unknown classification 500 → 400 (error code `ValidationError`); `POST /api/v1/rejection-reason-templates` without a name or reason keeps 400 with error code `ValidationError` (was `Error`); `POST /api/v1/folders` with a name the identifier policy rejects 500 → 400 in every locale; `GET /api/v1/secrets/{id}/certificate` and `GET /api/v1/secrets/{id}/access-log` by a machine token 500 → 400; `GET /api/v1/secrets/{id}/certificate` while the database is unreachable 500 → 503 `storage_unavailable`; `POST /api/v1/projects/{id}/access-review/revoke` of a role the principal does not hold 500 → 404, and on `.../access-review/revoke` and `.../access-review/attest` the "independent reviewer required" refusals (reviewing your own access, a group you belong to, or a machine identity you provisioned) 400 → 403 (the campaign route `POST .../access-review/campaigns/{campaignId}/items/{itemId}/decide` keeps 400); `DELETE /api/v1/projects/{id}/machine-identities/{machineId}/roles/{roleId}` for a role the machine does not hold 409 → 404 (parity with `DELETE /api/v1/user-roles` and gRPC `RemoveRole`); `PUT /api/v1/secrets/{id}` validation refusals answer 400 by sentinel in every locale (was 500 under a non-English locale).
- **A storage outage of the permission lookup inside a secret mutation answers 503, not 403 (#3873).** `PUT`/`DELETE /api/v1/secrets/{id}`, `PATCH .../description`, `PUT .../tags` and `POST .../move` authorize inside core; when that lookup failed (database unreachable) they answered 403 "access denied", which no client retries. They answer 503 + `Retry-After` with the fixed "authorization temporarily unavailable, please retry" now, as the gRPC `UpdateSecret`/`DeleteSecret` already did. A real denial stays 403. The last ten #3873 fault-oracle tolerance rows are gone.

### Fixed

The REST twin lands with #4165 (`TestEveryGrantingHandlerMapsTheCeilingRefusal`). The classifier's table is driven through both adapters (REST/gRPC parity on every sentinel), and `TestErrMap_StatefulFindingsAnswerDeclaredStatus` pins the #4132 findings under English and a translated pseudo-locale.
