### Changed
- **Several Keyorix nodes on one PostgreSQL: an audit batch no longer holds the audit lock across a client round trip.** A batch whose chain head the flusher does not know (every batch while two or more nodes append, the first after boot, the retry after a missed one-flight commit) used to take two flights: lock and head read, client hashing, then the INSERTs. It is now one flight in which PostgreSQL links the batch onto the head it reads under the same `KEYAUDIT` lock: the client sends each row's hash input without the predecessor hash, the statement computes `prev_hash`/`entry_hash` with `sha256()` and checks the stored rows link in id order before COMMIT. The chain bytes, audit-before-disclosure and durability are unchanged; the server re-checks every stored hash against its own encoding after COMMIT and fails the batch's reads (and stops linking) on any mismatch. A single node's steady state is unchanged. Design: `docs/specs/audit-pipelined-commits.md` ("Several Keyorix nodes"); guarded by `TestLinkedFlight_*` (PostgreSQL) and `INV-STORE-audit-linked-flight`.
