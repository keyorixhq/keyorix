### Security
- **A project role granted without a project no longer applies in every project (#3546, High).** A grant of `project_admin`, `project_developer`, `project_viewer` or `project_auditor` with no `project_id` was stored at the global scope, where it applies in EVERY project. The web UI's group *Manage Roles* sent exactly that, so a group member could become a developer of every project. Every grant path now refuses it with HTTP 400 / gRPC `InvalidArgument` ("role project_developer is project-scoped; specify a project_id"): user and group grants (permanent and time-bound), `PUT /users/{id}/roles`, user creation and global invitations with a project role as `role`, access-request approval, break-glass, machine-identity grants, and SSO JIT provisioning. An `environment_id` without its `project_id`, or one from a different project, is refused the same way. Global grants of `system_*` and the legacy `admin`/`editor`/`viewer`/`auditor`/`super_admin` roles are unchanged, per-project grants of the legacy roles to machine identities and users keep working as before (for example `keyorix machine grant-role <name> --project default --role viewer`, `keyorix rbac assign-role --user <email> --role admin --project payments`), and custom roles are unchanged, whatever their name.
- **Review existing grants after upgrading.** Grants written before this release are left as they are, because some may be relied on. At startup the server logs a `WARNING` for each user or group that holds a project role at the global scope. For each one, grant the role on the intended project(s), then remove the global grant. Any API client that has been granting project roles without `project_id` now gets 400 and must send the project.
- **SSO: project roles in `default_role` / `group_role_map` are refused.** Both settings grant at the global scope. With a project role as `default_role`, JIT provisioning through that provider is refused until it names a system role (for example `system_viewer`). A project role in `group_role_map` is not granted, but the login still goes ahead and the `auth.sso_roles_synced` audit event records the refusal. The server logs a startup `WARNING` for each such setting. To give an IdP group project access, map it to a Keyorix group that has a project-scoped role grant.
- **Every grant route answers a scope refusal with 400.** Project member add and role change, access-request approve (single and bulk), break-glass, membership invite/transition and project invitations answer HTTP 400 / gRPC `InvalidArgument` instead of 500. SSO/SAML sign-in refused for the provider's `default_role` shows "ask your administrator to fix the provider's default_role".
- **Accepting an old invitation that grants a project role install-wide** fails before the account is created and before the link is used up (it still answers the generic setup-link error; the reason is in the audit log). Revoke such invitations and send new ones with a project.
- **A failed `PUT /users/{id}/roles` no longer drops a legacy grant**: the undo of a partial update restores a pre-existing global project-role grant it had removed.
- **SSO JIT provisioning reads and checks `default_role` in the transaction that grants it**, before any write; if the role cannot be read the sign-in of the new user is refused and nothing is written.
