### Changed
- **Stricter validation of responses from external backends.** Responses that do not have the expected shape are now errors instead of being accepted. Vault connector: the mount-info reply must carry `data.path` and either a null/absent `options` (KV v1) or `options.version` of `"1"` or `"2"` (a refused reply is not cached); an empty or non-object KV payload is not a successful read; the token lookup must carry a numeric `data.ttl` (an explicit `0`, as reported for root tokens, is unchanged). Kubernetes dynamic engine: only 2xx statuses are success for TokenRequest, Secret create and Secret delete, and `Issue` requires a parsable, future `expirationTimestamp`. k8ssync Keyorix fetcher: only 2xx statuses are accepted, an empty or missing secret value is an error, an environment or secret id of 0 is refused, and server-supplied error text is stripped of control characters, truncated and quoted before it is logged.
- **Bounded redirect handling.** The JWKS, OIDC discovery, evidence webhook, SIEM forwarder and notification webhook clients refuse a redirect after three requests, compare the full host (port included) instead of the hostname, and still refuse an https to http downgrade.
- **Azure Key Vault connector error bodies.** Non-success responses reach the Azure SDK with a short fixed body (status code, headers and a plain `error.code` are kept), so the SDK no longer parses attacker-sized nested error JSON. The server's error message text is no longer included in connector errors.
