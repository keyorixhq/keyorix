### Fixed
- **A storage outage no longer reads as "not found" or "unknown role" on the grant, create and own-revoke paths.** Revoking your own session or personal access token, creating a user with a system role or project assignments, validating a role grant, creating an environment, copying secrets between environments, approving a secret access request or a project access request, and inviting a project member used to turn ANY failed storage read of the session, token, role, project, environment or secret into the verdict for an absent one (404 "not found", 400 "unknown role", 409 "no longer exists"), so a database outage looked like a mistake in the request and the revoke of a still-valid credential looked already done. A read fault is now `core.ErrStorageReadUnavailable`: REST answers 503 with `Retry-After` and code `storage_unavailable`, gRPC user create answers `Unavailable`. An absent session, token, role, project or environment keeps its existing text and status. The REST dynamic-secret lease routes (`POST /dynamic-secrets/leases/{leaseID}/revoke` and `/renew`), which resolve the lease's scope in the authorization middleware, now answer a lease-read fault 503 `storage_unavailable` to a caller who holds the permission globally; everyone else keeps the 403 they get for an absent lease, so a fault adds no existence signal for them. Not yet covered: the setup-link accept path (`completeInvitationAccept`) and the grant/create paths of machine tokens and dynamic-secret configs and leases, which stay listed as exceptions in `TestNoStorageReadErrorFoldedIntoNotFound`.
