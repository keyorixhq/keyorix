### Security
- **The secret metadata cache-epoch trigger is re-checked every 30 seconds (PostgreSQL).** The per-read proof only showed that `trg_secret_nodes_cache_epoch` exists and is `ENABLE ALWAYS`. The owner of its function, which is the server's own database role, could replace the body with one that stamps nothing, change the function's `search_path`, or re-create the trigger as `AFTER` or with a `WHEN` clause. A row changed with direct SQL then kept its `cache_epoch`, and every warm replica kept serving the old row from its cache. The existing integrity job now also compares the function's body, settings and the trigger's definition with this release's, and the catalog rows' versions with the previous reading. When either differs, the server logs a `SECURITY:` line, increments `keyorix_secret_node_cache_epoch_tamper_total`, restores the trigger and bumps `cache_epoch` of every `secret_nodes` row so every replica re-reads. The migration no longer rewrites a function that is already correct, and re-creates a cache-epoch trigger whose definition differs. A superuser acting below SQL is not detected. Design and residual risk: `docs/design/trigger-rowdigest.md`.
