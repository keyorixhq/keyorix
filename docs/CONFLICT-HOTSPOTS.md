## What `merge=union` can and cannot do

`merge=union` is a git merge driver: it keeps both sides' lines in a conflicting hunk. It
applies only to merges that run git's own merge machinery (merging main into a branch,
a coordinator merge pass, `git merge-file`). **GitHub's server-side merge, "Update branch"
and the merge queue ignore merge attributes**, so union cannot clear a conflict GitHub
reports; it removes the conflict from the local "merge main" step that precedes it.

Union is wrong where order or uniqueness matters, or where two PRs edit the same existing
line (the merge then keeps the old and the new version).

## Decision per file

Applied (`.gitattributes`, proved by `TestGitattributesUnionLedgers`): the five
exemption/override ledgers whose rows are independent lines, one row each, with no order:
`docs/atomicity-exempt.tsv`, `docs/besteffort-exempt.tsv`, `docs/full-row-write-exempt.tsv`,
`docs/child-parent-liveness-exempt.tsv`, `docs/state-map/class-overrides.tsv`. A key added
twice shows up twice and is caught by the ledger's guard test.

Left alone, on purpose:

- **Dual-read ledgers** (`adr-conformance-enforced.tsv`, `review-coverage.tsv`,
  `check-then-act-lock-exempt.tsv`): new rows already go in `<name>.d/`; union on the flat
  file would only hide edit conflicts there.
- **ADR numbers**: uniqueness matters, so no union. Use `~/proj/prompts/bin/adr-reserve`.
- **Generated files** (`docs/state-map/entrypoints.tsv`, `stores.tsv`, `openapi.yaml`,
  `api-generated.ts`, `faulty_storage_generated.go`): on a conflict take main's file and
  run the generator (`go run ./cmd/statemapgen`). A union merge would leave duplicate or
  stale rows that the generator then rewrites anyway; the drift guard
  (`internal/statemap/completeness_test.go`) is the safety net.
- **Sorted lists** (`internal/config/testdata/config_surface_leaves.txt`, the
  `docs/operations/metrics.md` table, `docs/README.md` index, threat-model index): union
  can leave them out of order. The coordinator already sorts and de-duplicates the first.
- **Wiring files** (`server/main.go`, `config.go`, `factory.go`, `values.yaml`): code, never
  union. Keep edits tiny and last (COMMON-RULES "HOT WIRING FILES").
- **`BACKLOG.md`, `web/BACKLOG.md`**: status lines are edited in place, so union would
  duplicate them.

## Fragment proposal for the prose hotspots (not implemented here)

`docs/CONFIGURATION.md` (42 merged PRs), `docs/UPGRADING.md` (28) and `docs/SELF_HOSTING.md`
(19) are edited by feature PRs for one reason: each adds its own setting, upgrade note or
section. The same pattern as `changelog.d/` fits:

- `docs/upgrading.d/<PR-or-slug>.md`, one fragment per PR, assembled into the "Unreleased"
  section of `docs/UPGRADING.md` by a script with a `--check` mode (copy
  `scripts/changelog-assemble.sh`);
- the same for `docs/CONFIGURATION.md` only for new-setting entries, with the generated
  config reference left as is.

This changes how three documents are authored and needs a decision on the assembled
output (committed or generated at release), so it is left for a follow-up.
