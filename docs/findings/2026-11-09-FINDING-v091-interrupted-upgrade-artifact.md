# v0.91.0 interrupted-upgrade "column never added": harness artefact on the real path

Classification: ARTIFACT (of the SQLite leg's interruption harness), with a residual
HARDENING note below.

## What was reported

The SQLite leg of the upgrade fuzzer (branch `fuzz/migration-upgrade`, report w3)
recorded a DEFECT: an upgrade from v0.91.0 stopped at write statement 34 or later
leaves `secret_nodes` without `owner_machine_identity_id`, and every secret read then
fails permanently. It was pinned as a defect by a test, since replaced by
`TestUpgradeInterrupted_V091_BarePathArtefact`.

## What this leg found

That test's interruption called `migrateDatabase` directly on an autocommit
connection (`ugInterruptedMigrate`). No production boot does. `createLocalStorage`
runs the migration through `withMigrationLock`, which holds one `BEGIN EXCLUSIVE`
transaction across the whole of it (`withSQLiteInDBMigrationLock`,
INV-STORAGE-23). A stop on that path rolls back everything, including the
`mfa_step_up_grants` table whose presence is what made the bare-path restart skip
the fresh-install tail.

PostgreSQL has the same structure by code reading (`withMigrationLockPooled` wraps
`migratePostgres` in one `db.Transaction`), and this is now CONFIRMED on a real
PostgreSQL 17 server (W6 continuation run, 2026-11-10; see the PG evidence section
below). The real locked path recovers cleanly from every interruption point; the
bare `migrateDatabase` path reproduces the exact SQLite defect on PostgreSQL too.

`TestUpgradeInterrupted_V091_SQLite_RealPath`
(`internal/storage/upgrade_pg_redproof_test.go`) takes the real path with the same
fail-stop callbacks at statements 34, 41 and 200. It asserts the stop was reached
(the migration returned the injected error and at least that many statements were
seen), restarts through `CreateStorage`, and reads a secret. It passes, while
`TestUpgradeInterrupted_V091_BarePathArtefact` asserts the bare path still reproduces it.

Replayed 3 times on the same tree, same result.

## PostgreSQL evidence (W6 continuation run, 2026-11-10)

Against a local PostgreSQL 17.11 server, with the v0.91.0 PG snapshot generated by
v0.91.0's own core, `TestUpgradePGInterrupted_V091_Compare` fail-stops the migration
at write statements 34, 41, 60 and 200 and compares the two paths. `pgRun` goes
through the real `CreateStorage` → `withMigrationLockPooled` boot on the real path.

Real locked path — recovers cleanly at every stop:

    real path stop=34  findings: []
    real path stop=41  findings: []
    real path stop=60  findings: []
    real path stop=200 findings: []

Bare `migrateDatabase` path (no outer transaction — not reachable in production, kept
only to mirror the SQLite leg's `ugInterruptedMigrate`):

    stop=34  oracle 6 fires: interrupted migration left the database changed (half-applied DDL)
    stop=41  oracle 6 fires: database changed
    stop=60  oracle 6 fires; AND oracle 7/8: secret_nodes.owner_machine_identity_id and its
             index/constraint missing; AND oracle 1: GetSecretValue(1..5) ->
             "column secret_nodes.owner_machine_identity_id does not exist (SQLSTATE 42703)"
    stop=200 clean (fewer than 200 write statements, so nothing was interrupted)

The bare path reproduces the SQLite defect byte-for-byte in meaning on PostgreSQL —
the exact `owner_machine_identity_id` column is never added and every secret read
fails — confirming the defect is real *for that unreachable shape* on both backends.
The real path leaves nothing behind because PostgreSQL DDL is transactional and the
whole migration commits or rolls back as one unit. `TestUpgradePGInterrupted_AtomicityOracle_RedProof`
pins this directly: at stop=60 oracle 6 fires on the bare path and is silent on the
real path, same state, same statement. Replayed (the compare test runs each stop in
its own subtest; the atomicity red-proof and the SQLite real-path test ran alongside,
all green).

Conclusion unchanged and now backed by PostgreSQL: on the real, locked boot path the
v0.91.0 interrupted-upgrade "column never added" condition does not occur on either
SQLite or PostgreSQL. It is an ARTIFACT of interrupting `migrateDatabase` outside the
migration transaction.

## Residual note (HARDENING, not a defect)

The bare-path result is still a true statement about `migrateDatabase` itself: the
fresh-install tail is the only thing that adds `owner_machine_identity_id` to a
v0.91.0 schema, and that tail is gated on `mfa_step_up_grants` being absent. Atomicity
is what keeps that gate honest. If `migrateDatabase` is ever called outside the lock,
or a step is moved out of the transaction, the defect becomes real. v0.91.0 is also
below the documented v0.93.x upgrade floor.

## Effect on the harness (done)

`ugInterruptedMigrate` now interrupts `migrateSQLite` through `withMigrationLock`,
the call `createLocalStorage` makes, so `FuzzUpgradeInterrupted` covers v0.91.0 and
`ugInterruptibleFrom` is gone. The bare path survives only as the red-proof option
`ugHooks.bareInterrupt`; `TestUpgradeInterrupted_V091_BarePathArtefact` records that
it fires and that the real path, same source and stop, is clean.
