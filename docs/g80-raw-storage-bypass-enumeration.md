## Discrepancy resolution: 145/87/58 is correct, not 149/90/59

`docs/g80-remediation-notes.md`'s #1547 entry (written 2026-08-23) records "149 flagged
call sites: 90 read-shaped... leaving 59 write-shaped candidates." That count was never
itself checked into a reproducible artifact — only the aggregate numbers were written
down, and the methodology note ("re-measuring the guard's real detection logic, not a
cruder estimate") asserts but does not demonstrate reproducibility.

Two independent implementations of the stated methodology (does an EXPORTED
`*KeyorixCore` method call `c.storage.X(...)`; does a router.go-registered handler call
`Storage().X(...)` for that same `X`; exclude `Get*`/`List*`/`Count*`/`Export*` as
read-shaped) were built and run against the identical commit:

1. A regex/line-scan version (brace-depth tracking across raw lines).
2. `scripts/analysis/raw_storage_bypass_enumerate.go`, a `go/ast`-based version — parses
   real syntax trees, so line-wrapping, multi-line chains, and comment placement cannot
   affect the result at all.

**Both produced exactly 145 total flagged call sites / 87 read-shaped / 58
write-shaped.** Two hypotheses for the gap were checked directly and ruled out:

- **Multi-line method chains** (`h.coreService.\n\tStorage().\n\tX(...)`) — grepped for
  every line ending in `coreService.` or `Storage()` or `c.storage.` across
  `server/http/handlers` and `internal/core`; zero matches outside test files. The
  AST version is immune to this class of formatting difference by construction anyway
  (an `ast.CallExpr` doesn't retain line-break information), and it still produced 58,
  not 59 — confirming line-wrapping was never the cause.
- **Variable/interface dispatch** (`x := h.coreService.Storage(); x.Method(...)`) — the
  AST tool explicitly tracks local aliases bound to a `.Storage()` call result and
  matches calls through them (see `[via local alias]` annotations, of which there are
  currently **zero** in the write-shaped list below). This category is real in
  principle (see the blind-spot doc) but contributes 0 to today's gap.

**Conclusion: 149/90/59 could not be reproduced and should be treated as the incorrect
figures pending a concrete counter-example** (e.g., someone finds the 59th write-shaped
call site by hand and it turns out to be real). 145/87/58 is what this document's number
is based on. The `docs/g80-remediation-notes.md` and `docs/g80-overnight-handoff-2.md`
entries from the same night both use 58/59 language inconsistently for this reason —
treat any reference to "59" from that session as superseded by this document's 58.

## Interprocedural blind spot closed: 30 → 42 write-shaped (2026-08-25)

The tool's `exportedCoreStorageWrappers` only ever looked at an EXPORTED
`*KeyorixCore` method's OWN body for `c.storage.X(...)` calls. It missed the
case where the exported method is a thin forwarder to an UNEXPORTED
same-receiver sibling that does the real work — e.g. `InviteMember` calls
`inviteMemberWithMode` (unexported), which is the one that actually calls
`c.storage.CreateProjectMembership(...)`. Because the tool never saw
`CreateProjectMembership` as "wrapped," `CreateMembershipProxy`'s raw call to
that same primitive went completely undetected as a bypass candidate — not
misclassified, simply invisible. Found during the G80 documented-exception
re-verification sweep's Task 2 handler-by-handler review, not by this tool
itself (it can't report what it can't see).

**Fix: one hop.** `exportedCoreStorageWrappers` now also inspects, for every
exported method, every unexported same-receiver sibling method it calls
directly, and folds THAT method's `c.storage.X(...)` calls into the wrapped
set too. Deliberately one hop, not unlimited recursion — see below for why
that turned out to be the right call, empirically, not just a guess.

**Predicted, then measured:** the specific prediction was that
`CreateMembershipProxy` would newly appear (via `CreateProjectMembership`,
one hop through `inviteMemberWithMode`). Confirmed: it does.
`UpdateMembershipProxy` does NOT newly appear — `storage.UpdateProjectMembership`
has no `internal/core` caller at all, direct or indirect, so there was never
a hidden wrapper for the one-hop extension to find there; that handler's
status is unchanged by this fix (correctly so — nothing was actually missed
for it).

**Is one hop enough, or does this need a second hop (or unlimited depth)?**
Measured directly, not assumed: a throwaway unlimited-depth BFS variant (walk
every unexported sibling transitively, not just one level) was run against
the same tree. It found 11 MORE wrapped storage methods overall (374 vs 363)
and 4 more total flagged call sites (150 vs 146) — but the **write-shaped
candidate list was byte-for-byte identical, 42 == 42, zero additions.** Every
additional method the deeper walk found was read-shaped (`Get`/`List`/`Count`/
`Export` prefix, already excluded regardless of depth). Conclusion: for the
current codebase, one hop already finds every write-shaped bypass candidate a
same-package unexported-forwarder chain can hide; a second hop would add
real implementation cost (recursive traversal, cycle detection for mutually-
recursive unexported helpers) for zero additional security-relevant findings
today. Not a permanent guarantee — a future call chain could go two hops deep
to a write-shaped primitive — but not worth building speculatively against a
codebase shape that doesn't currently exhibit it. If a future re-run of the
1-hop version diverges from a from-scratch unlimited-depth check like this
one, that's the signal to actually build the deeper version, not a guess in
advance.
