# Keyorix v0.97.0 — release notes

v0.97.0 is a minor release with **breaking changes**. If you run v0.96.x, read
[Before you upgrade](#before-you-upgrade) first, then
[UPGRADING.md §6k](../UPGRADING.md#6k-v0970-breaking-changes-at-a-glance) and the
[v0.97 upgrade checklist](../operator/upgrade-checklist-v0.97.md).

The complete list of changes is the `## v0.97.0` section of [CHANGELOG.md](../../CHANGELOG.md).
This page is the short version: what an operator has to do, and what a first-time user
walking the product will notice.

**Supported upgrade path.** v0.96.x to v0.97.x is supported. Coming from an older release,
step through each minor and read its notes
([VERSIONING.md](../VERSIONING.md)).

**Rollback is a restore.** v0.97.0 raises the schema compatibility floor (floor 3, schema
epoch 10). A v0.96.x binary refuses to start on a database a v0.97 server has started
against, and nothing lowers the floor. Take a backup before upgrading
([UPGRADING.md §6q](../UPGRADING.md), [upgrade-rollback.md](../operator/upgrade-rollback.md)).

## Before you upgrade

| Change | Who is affected | What to do | Details |
|---|---|---|---|
| The CLI refuses secrets given as flags (`--password`, `--value`, `--mfa-code`, and others) | scripts and CI that call `keyorix` | pass them through `KEYORIX_*` / `KEYORIX_*_FILE`, stdin or `--from-file` | UPGRADING §6l |
| CLI webhook URLs and tokens stay off the command line | scripts that pass a notification `--url` | use `--url-file` or the environment | UPGRADING §6x |
| CLI exit codes 2 to 6 | scripts that test for exit code 1 | branch on 0 to 6 | UPGRADING §6m |
| `KEYORIX_BOOTSTRAP_TOKEN` shorter than 32 characters is refused | installs that pin a short token | use a longer token, for example `openssl rand -hex 32` | UPGRADING §6g |
| `server.grpc.tls.auto_cert: true` is refused | configs with that line | remove it and give gRPC a certificate | UPGRADING §6t |
| `mfa.failed` and the other `*_failed` audit rows are stored with `success=false` | SIEM rules, exports, reports | match older history on `event_type` | UPGRADING §6u |
| PostgreSQL `session_replication_role` must be `origin` | databases or roles that set another default; Helm `postgresql.settings` | remove the setting before the new server starts | UPGRADING §6n |
| Grants fail closed when their audit row cannot be written | automation that creates users, roles, shares or tokens | after a 500 on those calls, check whether the object or grant already exists before retrying | UPGRADING §6o, §6o.1 |

| PostgreSQL `verify-full` / `verify-ca` needs `ssl_root_cert`; `ssl_mode` is an allowlist; Compose Postgres runs over TLS | external PostgreSQL, Compose | see the section | UPGRADING §2 |
| `admin init` writes `environment: production`; `development` replaces `allowed_origins` | hand-written configs that say `environment: development` | use `production`, `staging` or `local` | UPGRADING §6b |
| Roles carry an assignable scope; the legacy roles (`admin`, `editor`, `viewer`, `auditor`, `super_admin`) are install-wide only | API clients that grant roles on a project | send `assignable_scope` on role create; grant `project_*` roles on a project | UPGRADING §6z, `docs/upgrading.d/legacy-roles-install-wide-only.md` |
| Project names are unique ignoring case and Unicode normalization (schema epoch 10) | installs with two live projects whose names fold to the same value | the server refuses to start and changes nothing; with it stopped, rename one project of each listed group (the SQL is in the note) | `docs/upgrading.d/project-name-folded.md` |
| Setting a member's roles checks authority over every requested role | automation that calls the member-roles or user-roles endpoints | the same request can now answer 403 | `docs/upgrading.d/role-set-ceiling-every-requested-role.md` |

| `admin backup` on PostgreSQL refuses while its key directory holds a stale DEK | backups taken from any replica right after a DEK rotation | distribute the new key set first | `docs/upgrading.d/admin-backup-refuses-stale-dek.md` |
| Dynamic-secret configs whose `admin_dsn` names a server file fail on issue and renew | dynamic-secret configs stored before #3952 | remove the option; see the note | `docs/upgrading.d/dynamic-admin-dsn-revoke-strips-file-options.md` |

### Right after the upgrade: `audit verify`

On the first start after an upgrade from v0.96.x, the server now re-walks the audit chain at
once, because v0.96.x left no record that a full verification had completed. The start log
shows `Audit-checkpoint scheduler enabled ... first tick in 0s`.

- A chain of up to 100,000 audit events is covered by that first re-walk, so a plain
  `keyorix audit verify` reads `VALID`.
- A longer chain is re-walked in 7 segments, one per daily tick. Until the last one, plain
  `audit verify` reads `NOT PROVEN`. That is the fail-closed answer, not damage to the chain.
  Run `keyorix audit verify --full` once to prove the whole chain now.
- A chain with an edited row still reads `BROKEN` and names the first bad event.
  The meaning of `VALID`, `NOT PROVEN` and `BROKEN` did not change.

A post-upgrade check script should call `keyorix audit verify --full`: it gives the same
answer for every chain length. Details: `docs/upgrading.d/audit-verify-after-v096-upgrade.md`.

## What a first-time user will notice

These are the fixes that came out of walking the product end to end with the release
binaries ([docs/demo/GOLDEN-PATH.md](../demo/GOLDEN-PATH.md) is the script).

- **Audit search finds machine identities.** `keyorix audit search --actor <name>`
  (`GET /api/v1/audit/search?actor=`) now also matches machine identities by a partial,
  case-insensitive name, so a name shown in the ACTOR column can be searched for. Before, only
  user names matched.
- **Break-glass events name the person.** The `break_glass.activated` and
  `break_glass.revoked` audit descriptions say `user 2 ("dana")` instead of a bare `user 2`,
  and the break-glass list response carries the username. When the name cannot be read, the
  bare id stays.
- **A missing key directory is reported as a missing key directory.** `keyorix-server admin
  encryption init` and the other key-directory commands used to say a live server might be
  using the key directory. They now say that only when another process really holds the key
  lock. A missing directory reads: ``key directory <dir> does not exist: run `keyorix-server
  admin init` (or create it with mode 0700)``.
- **Clearer next steps in the CLI.** After `admin recover-admin`, a session that must set its
  own password is told to run `keyorix change-password` and then `keyorix mfa enroll`.
  `keyorix system init` with a wrong bootstrap token says to check `KEYORIX_BOOTSTRAP_TOKEN`
  or `KEYORIX_BOOTSTRAP_TOKEN_FILE` against the token the server started with. `user create
  --help` and `logout --help` describe what they really do, and every `--role` example in the
  help is a role that exists (`project_developer`, not `developer`).
- **Tampered audit rows are explained in plain words.** `admin verify-audit` now says the
  recorded `entry_hash` does not match the row's contents and the row was changed after it was
  written. Result fields, exit codes and JSON keys are unchanged.
- **`keyorix secret versions` no longer prints an internal note** about size and algorithm
  columns.
- **`keyorix logout` keeps your server URL and `ca_file`.** It revokes the session and removes
  the token; the next `login` against a server with a self-signed certificate works without
  repeating `keyorix config set ca_file`. To forget them too, run
  `keyorix config unset ca_file`. (v0.96.3 and older deleted the whole file.)

## Also in this release

Each item links to its documentation; the full list is in CHANGELOG.md.

- **Audit durability.** `storage.database.audit_durability` is `strict` or `standard`
  (default `standard` on PostgreSQL). UPGRADING §6c.
- **Multiple server replicas.** `storage.encryption.key_dir_lock: database` coordinates
  replicas, each with its own key directory, through the database; the Helm chart accepts
  `server.replicas` above 1 in Secret mode.
  [multi-replica-keys.md](../multi-replica-keys.md).
- **PgBouncer.** `storage.database.pooler` supports session and transaction pooling.
  [postgresql-poolers.md](../postgresql-poolers.md).
- **Single-writer mode** for PostgreSQL, one server only (`storage.database.single_writer`).
  [single-writer.md](../single-writer.md), UPGRADING §6f.
- **Break-glass** has a tab on the web project page, and keeps working in a degraded mode
  while the audit log is down (`break_glass.degraded_ttl`). UPGRADING §6o.1.
- **Incremental audit-chain verification** runs in the background instead of on the request
  path, which is why the first-start behaviour above exists.
- **`keyorix doctor`**, a read-only first-line checklist for a CLI install
  ([cli-reference.md](../cli-reference.md)).
- **Structured logs.** `server.log.format: json` writes one JSON object per log line.
- **Listener limits.** REST headers are limited to 64 KiB (431), and gRPC has idle,
  handshake, stream and metadata caps. UPGRADING §6p.
- **Crypto inventory scoring** is configurable with `crypto_inventory.quantum_horizon`,
  `migration_years` and `unbounded_lifetime_years`; the settings change the reported score
  only and nothing is enforced ([design-crypto-inventory.md](../design-crypto-inventory.md)).

## Helm

No value was renamed or removed. New values are additive: `server.singleWriter`,
`server.replicas` above 1 with `server.keysSecret.*`, `server.podDisruptionBudget.*`,
`server.topologySpreadConstraints`, `web.topologySpreadConstraints`, `server.trustedProxies`,
`server.accessLog.onSinkStall`, `server.goMemLimit` / `server.goMemLimitPercent`,
`server.probes.*`, `postgresql.settings`, `auditDurability`,
`externalDatabase.{sslRootCert,caSecret,pooler}`, `networkPolicy.egress.{databaseTo,kmsTo,kmsPorts}`,
`networkPolicy.ingress.*` and `monitoring.serviceMonitor.*`.

Two behaviours to know, both checked with `helm template`:

- `server.replicas` above 1 fails the render unless Secret mode is on
  (`server.keysSecret.enabled=true`, `server.keysSecret.name`,
  `server.keysPersistence.enabled=false`): every replica reads the same key files read-only.
  `singleWriter` must be false with more than one replica.
- `postgresql.settings.session_replication_role` is rejected by `values.schema.json`.

`postgresql.auth.password` no longer has an empty placeholder in `values.yaml`; the render
already failed when it was unset.
